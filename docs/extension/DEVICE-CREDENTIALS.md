# Extension Device Credentials — Storage & Reconnect

_How the browser extension persists connections across browser restarts and invite code changes, so users never have to re-enter a join code after first launch._

**Related docs:**

- [GUEST-AUTH.md](GUEST-AUTH.md) — player guest auth and first-time join flow
- [DM-LINK.md](DM-LINK.md) — DM-specific first-time link flow
- [EXTENSION-INTEGRATION.md](EXTENSION-INTEGRATION.md) — overall extension architecture
- [../CONTRACTS.md](../CONTRACTS.md) — locked API contract for credential issuance and exchange

---

## Overview

The join code (player invite link) is used exactly once — to establish the connection between a DDB user and a vtt-chat campaign. After that, a **device credential** stored in `localStorage` is the sole reconnection mechanism. The join code may be rotated at any time without affecting users who have already connected.

```text
First time:  invite code → guest-login / dm-link → deviceCredential stored
Every time after:  deviceCredential → credential/exchange → fresh JWT → launch
```

---

## Storage Keys

All credential data lives in `localStorage` so it survives browser restarts.

| Key                                            | Shape                        | Used by                                     |
| ---------------------------------------------- | ---------------------------- | ------------------------------------------- |
| `player:<externalCampaignId>:<externalSystem>` | `StoredCredential`           | Player reconnect                            |
| `dmlink:<externalCampaignId>:<externalSystem>` | `StoredCredential`           | DM reconnect                                |
| `dmsync:<campaignId>`                          | `{ lastSyncAt: ISO-string }` | DM sync throttle (`chrome.storage.session`) |

```typescript
type StoredCredential = {
  campaignId: string // vtt-chat UUID
  deviceCredential: { credential: string; deviceId: string }
}
```

`externalCampaignId` is the DDB campaign ID scraped from the campaign page. `externalSystem` is `"dndbeyond"` (or the appropriate system identifier).

`chrome.storage.session` is used for the sync throttle only — it is intentionally cleared on browser close since throttle state doesn't need to survive restarts.

---

## Credential Shape

Both player and DM credentials share the same shape returned from the server:

```typescript
// Returned by POST /api/auth/extension/guest-login (when deviceId is sent)
// Returned by POST /api/auth/extension/dm-link
{
  credential: string // opaque, URL-safe base64, 24 random bytes
  deviceId: string // UUID v4 generated by the extension on first install
}
```

The `deviceId` is generated once on extension install and persisted in `localStorage`. It must be sent on every call that issues or exchanges a credential so the server can enforce the per-user-per-device uniqueness constraint.

## First-Time Player Join

// Response includes: { token, user: { campaignId, ... }, deviceCredential: { credential, deviceId } }

if (response.deviceCredential) {

## First-Time DM Link — Receiving the Credential

After dm-link completes, `/ext-launch` signals the extension on **two channels simultaneously** (see [DM-LINK.md §9](DM-LINK.md)). The extension must listen on both; it will normally receive exactly one.

> **Why not BroadcastChannel?** Chrome content scripts run in an isolated JavaScript realm. BroadcastChannel is realm-scoped, so a channel in the page and one in a content script don't communicate — even with the same name, even in the same tab. `window.postMessage` is used instead because content scripts share the page's `window` object in both Chrome and Firefox.

### Channel A — window.postMessage → content script (primary)

The ext-launch page calls `window.postMessage(payload, origin)`. The content script (injected into the vtt-chat domain) receives it because both share the `window` object. The content script then relays to the background.

```typescript
// content-script.ts — injected into the vtt-chat domain
// Manifest: "matches": ["https://your-vtt-chat-domain.com/*"]

let handled = false // prevent double-store if both channels fire

window.addEventListener('message', (event: MessageEvent) => {
  // Only accept messages from the vtt-chat origin — not other frames or extensions
  if (event.origin !== VTT_CHAT_ORIGIN) return
  if (event.source !== window) return // must come from the page itself
  if (event.data?.type !== 'VTT_CHAT_DM_LINK_COMPLETE') return
  if (handled) return
  handled = true

  // Relay to background (MV3: service worker; MV2: background page)
  chrome.runtime.sendMessage(event.data) // Firefox: browser.runtime.sendMessage
})
```

```typescript
// background.ts (service worker)
// Background knows externalCampaignId + externalSystem from when it opened the tab

chrome.runtime.onMessage.addListener((message) => {
  if (message?.type !== 'VTT_CHAT_DM_LINK_COMPLETE') return
  storeDmCredential(message.payload)
})
```

### Channel B — window.opener.postMessage (fallback)

Fires when the extension popup used `window.open()` to open the tab. Listen in the popup script:

```typescript
// popup.ts
let handled = false

window.addEventListener('message', (event: MessageEvent) => {
  if (event.origin !== VTT_CHAT_ORIGIN) return
  if (event.data?.type !== 'VTT_CHAT_DM_LINK_COMPLETE') return
  if (handled) return
  handled = true
  storeDmCredential(event.data.payload)
})
```

### Shared storage helper (background + popup)

```typescript
function storeDmCredential(payload: {
  campaignId: string
  deviceCredential: { credential: string; deviceId: string }
  merged: boolean
}) {
  const { campaignId, deviceCredential } = payload
  // externalCampaignId + externalSystem are known from when the ext-launch tab was opened
  localStorage.setItem(
    `dmlink:${externalCampaignId}:${externalSystem}`,
    JSON.stringify({ campaignId, deviceCredential } satisfies StoredCredential)
  )
}
```

## Credential Exchange (shared helper)

Both reconnect paths use credential exchange. Always store the rotated credential immediately — the old one is invalidated the moment the server responds.

```typescript
async function exchangeCredential(
  stored: StoredCredential,
  storageKey: string,
  apiBase: string
): Promise<string> {
  const res = await fetch(`${apiBase}/api/auth/extension/credential/exchange`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      credential: stored.deviceCredential.credential,
      deviceId: stored.deviceCredential.deviceId,
    }),
  })

  if (!res.ok) {
    // CREDENTIAL_INVALID, CREDENTIAL_EXPIRED_GUEST, CREDENTIAL_EXPIRED_FULL
    // Caller must remove the stored credential and fall back to first-time flow.
    const err = await res.json().catch(() => ({}))
    throw new Error(err.code ?? 'CREDENTIAL_INVALID')
  }

  // { token: string, credential: string } — credential is already rotated
  const data = (await res.json()) as { token: string; credential: string }

  // Update stored credential before returning — old one is now dead
  const updated: StoredCredential = {
    campaignId: stored.campaignId,
    deviceCredential: {
      credential: data.credential,
      deviceId: stored.deviceCredential.deviceId,
    },
  }
  localStorage.setItem(storageKey, JSON.stringify(updated))

  return data.token
}
```

## Player Reconnect

Called on page load when the user is a campaign member but not the DM.

```typescript
async function tryPlayerReconnect(
  externalCampaignId: string,
  externalSystem: string,
  apiBase: string
): Promise<'launched' | 'needs-invite-code'> {
  const key = `player:${externalCampaignId}:${externalSystem}`
  const raw = localStorage.getItem(key)
  if (!raw) return 'needs-invite-code'

  const stored: StoredCredential = JSON.parse(raw)

  try {
    const token = await exchangeCredential(stored, key, apiBase)
    // sessionId left empty — /ext-launch will call session/ensure itself
    window.open(
      `${VTT_CHAT_ORIGIN}/ext-launch?campaignId=${stored.campaignId}&token=${encodeURIComponent(token)}&sessionId=`,
      '_blank'
    )
    return 'launched'
  } catch {
    localStorage.removeItem(key)
    return 'needs-invite-code' // fall back to invite code entry
  }
}
```

## DM Reconnect

Called on page load when the DDB user is detected as the campaign DM.

**No password prompt.** The device credential is exchanged for a fresh JWT, which is passed directly to `/ext-launch` via the `?token=` param. The ext-launch token path validates it silently and redirects straight to the campaign workspace — no login form is ever shown.

```typescript
async function tryDmReconnect(
  externalCampaignId: string,
  externalSystem: string,
  apiBase: string
): Promise<'launched' | 'needs-dm-link'> {
  const key = `dmlink:${externalCampaignId}:${externalSystem}`
  const raw = localStorage.getItem(key)
  if (!raw) return 'needs-dm-link'

  const stored: StoredCredential = JSON.parse(raw)

  try {
    const token = await exchangeCredential(stored, key, apiBase)
    const authHeader = { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` }

    // dm-sync throttle: at most once per 10 minutes per campaign
    const syncKey = `dmsync:${stored.campaignId}`
    const lastSync = await chrome.storage.session.get(syncKey)
    const sinceLastSync =
      Date.now() -
      (lastSync?.[syncKey]?.lastSyncAt ? new Date(lastSync[syncKey].lastSyncAt).getTime() : 0)

    if (sinceLastSync > 10 * 60 * 1000) {
      await fetch(`${apiBase}/api/integrations/external/dm-sync`, {
        method: 'POST',
        headers: authHeader,
        body: JSON.stringify({
          campaignId: stored.campaignId,
          externalSystem,
          externalCampaignId,
          characters: [],
        }),
      }).catch(() => {}) // non-fatal — sync will retry on next launch
      await chrome.storage.session.set({
        [syncKey]: { lastSyncAt: new Date().toISOString() },
      })
    }

    // Confirm or create an IDLE session so the workspace has a sessionId on arrival.
    const ensureRes = await fetch(`${apiBase}/api/campaigns/${stored.campaignId}/session/ensure`, {
      method: 'POST',
      headers: authHeader,
    })
    const { sessionId = '' } = ensureRes.ok ? await ensureRes.json().catch(() => ({})) : {}

    // Open ext-launch with the fresh JWT — no password prompt shown.
    window.open(
      `${VTT_CHAT_ORIGIN}/ext-launch?campaignId=${stored.campaignId}&token=${encodeURIComponent(token)}&sessionId=${encodeURIComponent(sessionId)}`,
      '_blank'
    )
    return 'launched'
  } catch {
    localStorage.removeItem(key)
    return 'needs-dm-link' // credential invalid — fall back to first-time DM link flow
  }
}
```

## Page-Load Decision Tree

```typescript
// On DDB campaign page load — called from the extension background/content script

if (loggedInDdbUserId === campaignDmExternalUserId) {
  // User is the DM of this campaign
  const result = await tryDmReconnect(externalCampaignId, externalSystem, apiBase)
  if (result === 'needs-dm-link') showFirstTimeDmUI() // invite code + Link & Launch
} else if (userIsInCampaignMemberList) {
  // User is a campaign player
  const result = await tryPlayerReconnect(externalCampaignId, externalSystem, apiBase)
  if (result === 'needs-invite-code') showInviteCodeUI() // invite code entry field
} else {
  showNotAMemberNotice()
}
```

## Error Handling

| Exchange error code        | Meaning                                             | Required action                                  |
| -------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| `CREDENTIAL_INVALID`       | Credential not found, rotated elsewhere, or revoked | Remove from storage; show first-time flow        |
| `CREDENTIAL_EXPIRED_GUEST` | 90-day inactivity window elapsed; guest account     | Remove from storage; prompt for invite code      |
| `CREDENTIAL_EXPIRED_FULL`  | 90-day inactivity window elapsed; full account      | Remove from storage; prompt for email + password |

In all error cases remove the stale key before falling back. Re-running the first-time flow is safe — all server operations (dm-link, guest-login) are idempotent for an already-linked identity.

---

## Security Notes

- The JWT is **never** persisted to `localStorage`, `sessionStorage`, `chrome.storage`, or cookies. It lives only in background script memory and is lost when the browser is closed.
- The `deviceCredential` is what persists in `localStorage` — it is a long-lived opaque token that can be exchanged for a fresh short-lived JWT.
- Credentials are stored server-side as salted SHA-256 hashes; the plaintext is never persisted.
- Credential exchange is rate-limited: max 10 exchanges per `deviceId` per minute.
- Rotation on every exchange prevents replay of an intercepted credential.
- A user may revoke all their credentials from Account Settings → Connected Devices (`DELETE /api/auth/extension/credentials/:credentialId`).
