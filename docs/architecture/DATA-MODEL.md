# **DATA-MODEL.md**

# VTT‑Chat Data Model

_A relational schema for campaigns, sessions, presence, chat, notes, audio, and long‑term history._

---

## 📘 Overview

This document describes the **Postgres + Prisma** data model used by the VTT‑Chat platform.
It covers:

- Core entities (users, characters, campaigns)
- Session lifecycle
- Rooms & presence
- Chat & notes
- Audio presets & DM overrides
- Recordings & journals
- Import/export & telemetry
- Admin & audit logs

The schema is designed for:

- **High‑volume real‑time usage**
- **Long‑term campaign history**
- **DM authority & assistant DM roles**
- **Private chat & green room semantics**
- **Audio effects & environment state**
- **Recovery after Redis restart**
- **Searchability & analytics**

---

# 🧩 Core Entities

## **User**

Represents a real person.

Key points:

- Users may DM multiple campaigns
- Users may have multiple characters in the same campaign
- Users may have global and per‑campaign settings
- Users may be **guest accounts** created via the browser extension invite flow
- Guest users can be upgraded to full accounts without losing any campaign history

**Fields include:**

- `id`, `email`, `displayName`, `avatarUrl`
- `authType` — enum: `FULL` (has password) | `GUEST` (no password, created via extension)
- `passwordHash` — null for guest accounts
- `createdAt`, `updatedAt`

See [../extension/GUEST-AUTH.md](../extension/GUEST-AUTH.md) for the auth flow that creates and manages guest users.

---

## **Character**

Represents a player character in a specific campaign.

Key points:

- A user may have **multiple characters in the same campaign**
- Characters store rich metadata for long‑term campaign history
- Characters may be imported or synced from DDB/Roll20/FVTT via the extension
- Characters created via extension carry external system and ID tags for future sync

**Fields include:**

- `name`, `race`, `class`, `subclass`, `level`
- `status` (alive, dead, left, unknown)
- `notes` (markdown)
- `avatarUrl`
- `characterUrl`
- `externalSystem` — enum (nullable): which external platform this character originated from
- `externalId` — string (nullable): the character ID on the external platform (e.g. DDB character ID)

---

## **Campaign**

Top‑level container for:

- Characters
- Sessions
- Rooms
- Notes
- Chat
- Recordings
- Journals

Key points:

- DM can change over time
- Assistant DM roles are session‑scoped
- Campaigns have separate invite codes for players (extension-required) and spectators (web-only)
- The **player invite code** is campaign-scoped and applies to both players and the DM. Role (DM or Player) is determined server-side from the `dmExternalUserId` field in the extension's campaign data packet.
- The **first user to connect** bootstraps the campaign: the extension sends a campaign data packet containing the DM's external ID, all member external user IDs, and basic character info. The backend creates stub records for all listed members. Subsequent connections extend the data per `extensionSyncPolicy`.
- Player invite codes are generated by a full-account DM or sysadmin. A DM of any account type (or a sysadmin) can revoke or reissue the code at any time.
- Spectator invite codes can only be generated by a full-account DM.
- Campaigns have a recording mode
- Campaigns store a sync policy controlling whether extension data can update campaign/character records
- DM controls spectator access, slot limits, and waitlist behavior

**Fields include:**

- `currentDmId`
- `dmHistory[]`
- `recordingMode`
- `inviteCode` — player invite; campaign-scoped; covers both players and DM (role inferred from external data); one active code per campaign; generated by full-account DM or sysadmin; DM (any account type) or sysadmin may revoke or reissue
- `inviteActive` — boolean; false disables new player joins without removing existing members
- `spectatorInviteCode` — spectator invite; separate from player invite; opens web page (no extension required)
- `spectatorInviteActive` — boolean; false disables new spectator joins
- `spectatorPolicy` — enum: `NONE` | `GUESTS` | `USERS` (default: `NONE`)
  - `NONE`: spectators disabled; campaign appears in browse marked as private
  - `GUESTS`: guest and full-account spectators permitted
  - `USERS`: full-account spectators only
- `spectatorMax` — integer; null = use platform default; sysadmin sets platform default and hard cap
- `spectatorWaitlistEnabled` — boolean; when true, overflow spectators join a waitlist and are auto-promoted (first-come-first-served) when a slot opens
- `spectatorReconnectGraceSecs` — integer; seconds a disconnected spectator retains their slot before it is released (sysadmin-controlled default)
- `discoverable` — boolean; when true and `spectatorPolicy != NONE`, campaign appears in public browse list
- `extensionSyncPolicy` — enum: `NONE` | `DM_ONLY` | `DM_AND_PLAYERS` (default: `DM_ONLY`)
- `createdAt`, `updatedAt`

# 🎭 Sessions

A session represents a single play session.

Key points:

- Sessions begin in the **green room**
- DM starts the session → recap shown
- Session ends → return to green room
- Journals store manual + AI summaries
- Recordings attach to sessions

**Fields include:**

- `startedAt`, `endedAt`
- `recapShown`
- `journal` (1:1)

---

# 🏠 Rooms

Rooms represent audio/chat spaces:

- `GREEN_ROOM`
- `MAIN`
- `GROUP`
- `PRIVATE`

Key points:

- Private rooms are ephemeral
- Group rooms are DM‑created
- Rooms store recordings
- Room membership lives in Redis, but DB stores metadata

**Fields include:**

- `name`, `type`, `isActive`
- `createdAt`, `updatedAt`

---

# 🟢 Presence

Presence is **Redis‑first**, but Postgres stores snapshots for:

- Recovery after Redis failure
- Telemetry
- Analytics
- Session history

**PresenceSnapshot fields:**

- `campaignId`, `userId`, `sessionId`
- `primaryRoomId`, `privateRoomId`
- `state`
- `lastSeenAt`

# 💬 Chat System

Chat messages support:

- Room chat
- Whispers
- System messages
- External logs (DDB/Roll20/FVTT)
- Metagame messages
- Attachments (base64 images)

**Fields include:**

- `type` (ROOM, WHISPER, SYSTEM, METAGAME, EXTERNAL)
- `markdown`
- `attachments`
- `externalSource`
- `isGreenRoom`
- `isSystem`

Messages are immutable except for deletion flags.

# 🔌 External Integrations

## **ExternalIdentity**

Links a vtt-chat user to an account on an external system.

Key points:

- One user may have multiple `ExternalIdentity` records (one per connected system).
- Matching across systems is done by email address: if the same email appears from two different external systems, they resolve to the same vtt-chat user.
- Created automatically when a user first joins via the guest auth flow.

**Fields include:**

- `id`
- `userId` — FK to User
- `externalSystem` — enum: `DNDBEYOND` | `ROLL20` | `FOUNDRY` | ...
- `externalUserId` — string (the user's ID on the external platform)
- `email` — string (scraped from external profile, used as matching key)
- `lastSeenAt`
- `createdAt`

---

## **SpectatorWaitlist**

Tracks spectators waiting for a slot in a campaign that is at capacity.

Key points:

- One entry per user per campaign (a user can only be on one campaign's waitlist at a time).
- When a slot opens (spectator disconnects and reconnect grace period expires), the first-position entry is automatically promoted.
- Promoted entries are removed from the waitlist and a spectator JWT is issued.
- Waitlist is cleared when the session ends or spectators are disabled.

**Fields include:**

- `id`
- `campaignId` — FK to Campaign
- `userId` — FK to User
- `joinedAt` — timestamp (determines position; earlier = higher priority)
- `waitlistToken` — opaque token used by the client to poll for promotion status
- `promoted` — boolean
- `promotedAt` — timestamp (nullable)

---

## **CampaignExternalLink**

Links a vtt-chat campaign to a campaign on an external system.

Key points:

- A vtt-chat campaign may be linked to campaigns on multiple external systems simultaneously.
- Within one campaign, only one active link per external system.
- Links are created by the DM (or automatically when the DM's extension identifies the external campaign).

**Fields include:**

- `id`
- `campaignId` — FK to Campaign
- `externalSystem` — enum
- `externalId` — string (the campaign ID on the external platform)
- `linkedAt`
- `linkedBy` — FK to User (must be a DM of the campaign)

---

## **ExternalSystem** (Platform Registry)

Platform-admin-controlled registry of permitted external systems.

Key points:

- New systems start in `BLOCKED` state and must be explicitly authorized.
- Authorization state is separate from per-campaign sync policy.
- All state changes are audit-logged.

**Fields include:**

- `id`
- `systemKey` — stable lowercase identifier (e.g. `dndbeyond`)
- `displayName` — human-readable name
- `authorizationState` — enum: `AUTHORIZED` | `LOG_ONLY` | `BLOCKED`
- `allowedScopes` — array: `auth`, `log_ingestion`, `metadata_sync`
- `notes` — admin-visible notes
- `updatedAt`
- `updatedBy` — FK to admin User

See [../extension/THIRD-PARTY-INTEGRATIONS.md § 11](../extension/THIRD-PARTY-INTEGRATIONS.md) for admin controls.

# 🧠 Design Principles

### 1. **Redis is the source of truth for live state**

Postgres stores snapshots for recovery + analytics.

### 2. **Postgres is the source of truth for history**

Everything that matters long‑term is stored here.

### 3. **DM authority is explicit and logged**

DM changes, assistant DM roles, and overrides are all auditable.

### 4. **Notes and chat are first‑class citizens**

Searchable, timestamped, and exportable.

### 5. **Audio effects are declarative**

Presets are JSON, not code.

### 6. **Sessions are boundaries**

Everything is scoped to a session unless explicitly global.
